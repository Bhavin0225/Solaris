## 1. Problem statement

Build a web application that forecasts, for **Davanagere, Karnataka, India**, the next 72 hours of:

| # | Target | Unit | Type |
|---|---|---|---|
| T1 | Solar PV energy generation | kW (hourly mean) | Energy |
| T2 | Relative humidity (2 m) | % | Weather |
| T3 | Solar radiation, global horizontal irradiance (GHI) | W/m² | Weather |
| T4 | Wind speed (10 m) | m/s | Weather |
| T5 | Wind turbine energy generation | kW (hourly mean) | Energy |

The system is **multivariate**: all five targets are forecast jointly from shared inputs, because they are physically coupled. Radiation drives T1, wind speed drives T5, and humidity and temperature affect both radiation and PV efficiency.

## 2. Goals and non-goals

### Goals
- G1: Forecast T1–T5 hourly for horizons 1–72 h, refreshed at least every hour.
- G2: Show measurable skill over three baselines: persistence, climatology, and *raw Open-Meteo forecast + physics conversion* (§9.1).
- G3: Get all weather data **directly** from the NASA POWER and Open-Meteo REST APIs (no third-party wrappers or scrapers).
- G4: Validate the physics energy simulation against real plant data (Kaggle solar + wind) before using it as training targets.
- G5: Ship a clean, explainable website that a viva examiner can use live.

### Non-goals
- Multiple locations or a location picker (v1 is Davanagere only; keep the code location-agnostic so this is an easy v2).
- Real-time SCADA integration with a physical plant.
- Grid dispatch, pricing, or financial modelling.
- User accounts or authentication.

## 5. Data sources

All weather data is fetched **directly over HTTPS** with `requests`/`httpx`. Cache every raw response to disk so nothing is downloaded twice.

### 5.1 NASA POWER: historical "ground truth" for training

- **Endpoint:** `https://power.larc.nasa.gov/api/temporal/hourly/point`
- **Required query params:** `parameters`, `community=RE`, `latitude`, `longitude`, `start=YYYYMMDD`, `end=YYYYMMDD`, `format=JSON`, `time-standard=UTC`
- **Limit:** hourly requests accept **at most 15 parameters per call**. Request **one calendar year per call** and loop over years.
- **Period:** 2001-01-01 → most recent complete year *(verify hourly start year; recent months may lag)*
- **Missing value sentinel:** `-999` → convert to NaN
- **Politeness:** sequential requests, ≥1 s sleep, exponential backoff on HTTP 429/5xx.

**Parameters (14, fits in one call):**

| Parameter | Meaning | Used for |
|---|---|---|
| `ALLSKY_SFC_SW_DWN` | GHI (hourly, Wh/m² ≡ mean W/m²) | **T3**, PV sim |
| `ALLSKY_SFC_SW_DNI` | Direct normal irradiance | PV sim |
| `ALLSKY_SFC_SW_DIFF` | Diffuse horizontal irradiance | PV sim |
| `CLRSKY_SFC_SW_DWN` | Clear-sky GHI | Feature (clear-sky index) |
| `ALLSKY_KT` | Clearness index | Feature |
| `T2M` | Air temperature 2 m (°C) | PV cell temp, air density |
| `RH2M` | Relative humidity 2 m (%) | **T2** |
| `QV2M` | Specific humidity 2 m | Feature |
| `WS10M` | Wind speed 10 m (m/s) | **T4** |
| `WS50M` | Wind speed 50 m (m/s) | Hub-height extrapolation |
| `WD10M`, `WD50M` | Wind direction (°) | Features |
| `PS` | Surface pressure (kPa) | Air density |
| `PRECTOTCORR` | Precipitation (mm/h) | Feature |

**Hub-height wind (80 m) from NASA:** per hour, α = ln(WS50M/WS10M) / ln(50/10), clipped to [0.05, 0.40]; `ws_hub = WS50M × (80/50)^α`. If WS10M < 0.5 m/s, use α = 0.143.

**Timestamp alignment check (mandatory):** confirm whether NASA hourly values are labelled at the start or end of the averaging hour. Test: cross-correlate NASA GHI with pvlib clear-sky GHI for the site; the lag with the highest correlation tells you the offset. Document the result in `docs/data_notes.md`.

### 5.2 Open-Meteo: live forecasts (serving) and historical forecasts (training covariates)

Free for non-commercial use, no API key *(verify current terms and daily call limits)*. Always pass `timezone=GMT` and `wind_speed_unit=ms`.

| API | Endpoint | Role |
|---|---|---|
| Forecast | `https://api.open-meteo.com/v1/forecast` | **Live website input**: next 72 h (`forecast_days=3`, plus `past_days=7` for lag features) |
| Historical Forecast | `https://historical-forecast-api.open-meteo.com/v1/forecast` | **Training covariates**: archived past forecasts, so the model learns how Open-Meteo's forecast *errors* behave *(verify the earliest available date; it starts years later than NASA)* |
| Historical Weather (ERA5) | `https://archive-api.open-meteo.com/v1/archive` | Cross-check against NASA POWER; fallback covariates if the Historical Forecast API is too short |

**Hourly variables to request** *(verify names on open-meteo.com/en/docs; the archive API offers `wind_speed_100m` instead of 80/120 m)*:

```
shortwave_radiation, direct_normal_irradiance, diffuse_radiation,
global_tilted_irradiance (with tilt=15&azimuth=0),
temperature_2m, relative_humidity_2m, surface_pressure, cloud_cover, precipitation,
wind_speed_10m, wind_speed_80m, wind_speed_120m, wind_direction_10m, wind_direction_80m
```

**Known quirk:** Open-Meteo radiation values are the **mean over the preceding hour**. Align this with the NASA convention found in §5.1 before joining.

### 7.1 Stages

### 7.2 Cleaning rules
- Reindex to a complete hourly UTC index; report the % missing per column.
- Interpolate gaps ≤ 3 h linearly; leave longer gaps NaN and drop those windows from training samples.
- Clip to the physical ranges in §6; log every clipped value count.
- Night-time GHI forced to 0 where solar zenith > 90°.

### 7.3 Physics validation (acceptance gate before any ML)
**Solar:** on Kaggle Plant 1 (and Plant 2), aggregate AC power per timestamp, normalize by the plant's observed max, and fit against the measured irradiation. Run the same normalized comparison for the pvlib chain. Tune *only* the system-loss % (range 8–20%) to minimize the RMSE of normalized output. **Pass:** normalized nRMSE ≤ 10% on daytime rows *(target; adjust if justified)*.

**Wind:** on T1.csv, compare simulated power (empirical curve × availability) against `LV ActivePower (kW)`. **Pass:** nRMSE ≤ 14%. The raw manufacturer curve already scored 13.0% nRMSE in the pre-project test, so the simulation must not be worse than that.

Save scatter plots (simulated vs actual) and the metrics to `reports/validation/`. These go straight into the project report.

### 7.4 Source-consistency check (train/serve skew)
For the overlapping period, compare NASA POWER vs Open-Meteo ERA5 archive for GHI, RH, WS10M (bias, RMSE, correlation). If the bias is large, add a learned bias-correction or include the source difference as a feature. Document this in `docs/data_notes.md`.

### 7.5 Splits (strictly chronological, no shuffling)
- **Train:** start → end of year N−2
- **Validation:** year N−1
- **Test:** most recent complete year N (held out until final evaluation)
- Each split must contain full annual cycles (monsoon included).

## 8. Features

| Group | Features |
|---|---|
| Lags (from history) | Each target at t−1…t−6, t−12, t−24, t−48, t−168 |
| Rolling stats | 6 h / 24 h mean and std of each target |
| Known-future covariates | Open-Meteo forecast for target hour: radiation (GHI, DNI, DHI, GTI), temp, RH, pressure, cloud cover, precip, wind 10/80 m, direction |
| Solar geometry | Solar zenith, azimuth, clear-sky GHI (pvlib), clear-sky index |
| Calendar | Hour-of-day, day-of-year as **sin/cos pairs**; monsoon flag (Jun–Sep) |
| Wind direction | sin/cos of direction (never raw degrees) |
| Horizon | Lead time h (for direct multi-horizon models) |

**Lesson from the pre-project test:** a raw `day_of_year` integer feature made LightGBM *worse* (nRMSE 17.5% vs 14.0%) because the test months were outside the training range. Use cyclic encodings and multi-year data.

## 9. Modelling

### 9.1 Baselines (must be implemented first)
1. **Persistence:** value at t (and same hour yesterday for solar).
2. **Climatology:** mean of that hour-of-day × month over training years.
3. **NWP + physics (the real benchmark):** Open-Meteo forecast fed straight through the §4 physics chain, with no ML.

An ML model is only "better" if it beats **baseline 3** on the test set. Report the skill score: `1 − RMSE_model / RMSE_baseline3`.

### 9.2 Model ladder
| Model | Framing | Library | Purpose |
|---|---|---|---|
| LightGBM | Direct multi-horizon: one model per target, horizon as a feature (or per horizon bucket 1–6, 7–24, 25–72 h) | `lightgbm` | Strong tabular baseline, likely the deployed model |
| LSTM / GRU seq2seq | Encoder: past 168 h, all targets + covariates. Decoder: 72 h with known-future covariates. Output: 5 targets jointly | `pytorch` | The multivariate deep model |
| Temporal Fusion Transformer | Past observed + known future inputs, 5 targets, quantile outputs (P10/P50/P90) | `darts` or `pytorch-forecasting` | Interpretability (variable importance) + uncertainty bands |

### 9.3 Evaluation
- **Metrics:** MAE, RMSE, nRMSE (energy normalized by capacity; weather by the observed range), skill vs baseline 3.
- **Solar metrics computed on daytime hours only** (zenith < 85°), or night zeros flatter the score.
- **Breakdowns:** by horizon (1, 6, 24, 48, 72 h), by season (monsoon vs dry), by target.
- **Uncertainty (TFT):** P10–P90 interval coverage should be ≈ 80%.
- **Output:** `reports/evaluation/leaderboard.csv` + plots; the best model per target is written to `models/registry.json`.

### 9.4 Model selection rule
For each target, deploy whichever model has the lowest test RMSE **and** beats baseline 3. If no ML model beats baseline 3 for a target, deploy baseline 3 for that target and say so honestly in the report and the UI.

## 10. Backend

- **Framework:** FastAPI (Python 3.11+), served with Uvicorn.
- **Scheduler:** APScheduler job, hourly: fetch Open-Meteo forecast (+ `past_days=7`), build features, run models, cache the result.
- **Cache:** SQLite (`data/app.db`) with one row per (run_time, target_time, target, model, p10, p50, p90).
- **Fallback:** if Open-Meteo is unreachable, serve the latest cached forecast with a `stale: true` flag and its age.

Response timestamps are ISO-8601 UTC; the frontend converts them to IST.

## 16. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Energy targets are simulated, not measured | Examiner challenge | §7.3 validation against real plants; state the caveat clearly in the report and UI |
| NASA (satellite/reanalysis) ≠ Open-Meteo (NWP) | Train/serve skew, degraded live accuracy | §7.4 comparison; train on Open-Meteo *historical forecasts* as covariates |
| Open-Meteo Historical Forecast API covers fewer years than NASA | Less training data for the covariate model | Two-stage design: long NASA history for lag/seasonal learning, shorter covariate period for fine-tuning; ERA5 fallback |
| NASA 50 m vs Open-Meteo 80 m wind heights differ | Hub-wind bias | Use the same extrapolation method on both, or learn the correction |
| Low wind resource at Davanagere | T5 mostly near zero outside the monsoon | Report capacity factor honestly; evaluate wind metrics by season |
| API downtime or rate limits | Website shows nothing | Cached fallback with stale flag; backoff and retries |
| ML fails to beat the NWP baseline | Weak results | §9.4: deploy the best honest option and report it; this is a legitimate finding |

## Appendix A: Pre-project test results (already run)

|---|---|---|---|---|

| Power 1 h ahead | LightGBM (with raw day-of-year) | 463.6 | 633.4 | 17.5% |
| Power 1 h ahead | LightGBM (no day-of-year) | 329.8 | 504.9 | 14.0% |
